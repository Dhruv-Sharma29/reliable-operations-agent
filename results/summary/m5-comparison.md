# M5: scripted runbook vs simple agent vs durable agent

Same 30 cases for each responder (20 dev, 10 held-out). Every verdict comes from the runner: the
independent probe (`eval/verify.py`) and the scorer, never the agent's claims. Generated by
`python -m eval.compare results/summary/m5_manifest.json` (table also in `m5.md` / `m5.json`).
Per-case evidence, tool trace, action and uncertainty: `results/ui/m5_report.html`.

LLM agents: prompt v2 + schema-enforced final answer (v2s), Qwen2.5-7B-Instruct Q4_K_M on
llama.cpp, temperature 0, a stand-in approver for approval-required actions.

## Reading it

- **The scripted runbook wins outright: 30/30, in about 2 s.** That's expected and is the point of
  the baseline. Its rules were written from the incident catalogue, so it measures what's
  achievable with this evidence, not what's realistic for unseen incidents.
- **Both LLM agents succeed on about half: simple 15/30, durable 14/30.** Only 5 cases differ
  between them, 3 vs 2 (exact McNemar p = 1.0). The differences come from the model diagnosing
  differently between runs, not from the workflow. That's the expected result: durability is about
  surviving crashes without repeating effects, which is measured separately (8 crash tests, a
  mutation check, and a live crash demo with the real model; README, milestone 4). It isn't meant
  to make diagnoses better.
- **Behaviour does differ: the durable agent escalates more** (9 vs 5 of 30). Its workflow
  escalates whenever the diagnosis is `unknown` (3 cases) instead of proposing an action anyway.
  It also had fewer cases where an action "succeeded" but the service stayed unhealthy (2 vs 7).
  With 30 cases that gap isn't separable from noise. It's a hypothesis, not a finding.
- **Claimed vs verified.** In 9 of 60 LLM cases an action reported success but the independent
  probe found the service still broken: wrong target, wrong action, or not enough capacity. A
  scorer that trusted the agent's report would have counted those as recoveries.
- **Time to recovery isn't comparable across all rows.** The two LLM agents ran back to back on an
  idle shared GPU (~42 tokens/s); earlier runs in this project had ~5.5 tokens/s under other users'
  load, about 8x slower. The simple and durable rows are comparable with each other only.

## Durable agent in evaluation

The runner verifies health itself, so the durable responder skips the workflow's own VERIFYING
probe. Its `RESOLVED` state in these records is therefore **not** a health verdict; e.g.
`dev-queue_backlog-0` is `RESOLVED` while the probe says unhealthy. Every number above uses the
runner's probe.
